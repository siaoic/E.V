## P0 — 正确性 / 性能（建议立即处理）

### 1. ✅ 已修复：情绪向量化的延迟回归（⚠️ 原 v0.11 引入）

**现状（证据）**

- `ev/emotion/reaction.py`：`classify()` 是同步方法，内部走 `classifier.classify_sync()` → `ev/llm/utils/embedding.py` 的 `_run_sync()` → `asyncio.run_coroutine_threadsafe(...).result()` —— **在调用线程上阻塞等待**。
- 调用链：`ev/llm/stream.py:91`（speak_text）与 `ev/llm/stream.py:242`（converse）对**每一句**播报文本执行 `await emotion_actor.handle_rule(seg)` → 每句一次同步 embed 调用（本地 llama.cpp 实测单次 30~450ms）。
- 冷启动更糟：`ev/emotion/actor.py:104` 的 `initialize()` 是懒执行，且 `ev/kernel/components/avatar.py:38-42` 组件 setup 只做 `scan()/load_map()` **不预热**；若第一句话到来时才初始化，会当场 embed 全量语料（6 情绪 × 各 100+ 句 ≈ 1000+ 条），造成**数秒级**的播报停顿。
- 全量语料向量**没有任何持久化**（代码中无 npz/safetensors 缓存；`.gitignore` 里的 `data/emotion_embedding_cache.npz` 是历史遗留，无代码引用）→ 每次启动进程都重嵌一遍。

**问题**：v0.11 把 reaction 从零开销正则换成了向量，播报路径每句多了 1 次网络/推理 RTT，且都发生在 asyncio 主循环线程上——阻塞期间 TTS 排队、弹幕回调全部卡住。

**建议**

1. **异步化**：给 `MessageReaction` 增加 `async def classify_async()`（内部直接 `await classifier.classify()`），`BaseEmotionActor.handle_rule` 改为调用异步版；`stream.py` 两处调用点无需改动（本来就是 await）。同步 `classify()` 仅保留给非 asyncio 场景。
2. **启动预热**：`avatar.py` setup 里 `asyncio.create_task(actor.initialize())` 后台预热（不阻塞启动）；`BaseEmotionActor.initialize()` 成功后已注入共享分类器（v0.11 已做），确保 `handle_rule` 不再触发第二份语料 embed。
3. **向量持久化**：`EmbeddingEmotionClassifier.initialize()` 完成后把 `matrix + labels + (model, 语料哈希, 维度)` 存 `data/emotion_corpus_cache.npz`；下次启动哈希命中直接加载，跳过网络 embed。语料或模型变了自动失效重建。
4. **逐句并发**（可选）：`stream.py` 里对一次播报的多句先 `asyncio.gather` 批量 embed（provider 已有 `batch_embed`），再按句播放表情。

**收益**：播报路径每句省 30~450ms 的主循环阻塞；冷启动不再出现数秒级卡顿；进程重启零 embed 成本。

### 2. ✅ 已修复：`[SILENT]` 标记主对话路径剥离（⚠️ 原 v0.11 引入）

**现状（证据）**

- v0.11 在 `ev/llm/brain/chat/inner_loop.py` 把 `build_silence_prompt_patch()` 注入了系统提示——而 `chat_stream` 是**主对话与主动对话共用**的入口。
- 主动对话路径安全：`ProactiveEngine._parse_decision`（`ev/llm/proactive/core.py:308`）会吃掉 `[SILENT]`/`[END]`。
- 但**主对话路径（键盘/语音）没有任何剥离逻辑**：`converse()`（`ev/llm/stream.py:133`）逐句送 TTS，silence 钩子只挂在 `speak_text` 上，converse 自身的 final 句不经过它。

**问题**：模型在主对话里如果按协议输出 `嗯嗯 [SILENT]`，标记会被原样 TTS 念出来（"SILENT"），或 `[END]` 被念成"恩德"。

**建议**（推荐 a+c）

- a. `converse()` 的 final 句进 TTS 前过一遍 `ev.social.silence.strip_markers()`（纯剥离、不静默——主对话是用户点名，不该真沉默）；
- b. 备选：静默协议 prompt 段只注入 `proactive=True` 的请求（需要 chat_stream 按模式裁剪注入段，改动稍大）；
- c. `strip_markers` 同时覆盖 `<SILENT>`/`<END>` 变体，与 `_SILENT_MARKERS` 对齐。

**收益**：杜绝标记词被念出来的翻车现场；工作量约 10 行。

### 3. ✅ 已修复：跨线程状态安全

**现状（证据）**

- `ev/danmaku/client.py:320` `bili_loop` 在**独立线程**里跑自己的事件循环；`client.py:216` 直接调 `nudge.observe("danmaku", ...)`，v0.11 又加了 `ev.social.observe_danmaku(...)`。
- 被跨线程改写的状态：`NudgeEngine.burst_window`（list append，`ev/llm/proactive/nudge.py:195`）、`unread_count`、`last_activity_ts`——主循环线程同时在做 `check()` 读 + 滑动窗口重建（`nudge.py:229`）。
- v0.11 的 `ev/social/wake.py` `poke()` 在弹幕线程直接 `_event.set()`——`asyncio.Event.set()` **不是线程安全的**，且该 Event 与主循环可能不是同一个 loop。
- `bootstrap.observe_danmaku` 里 `asyncio.get_running_loop().create_task(...)`：在弹幕线程拿到的是 **bili 循环**，engagement/learning 的 task 跑在 bili 线程，状态又写回主循环读取的对象。

**问题**：CPython 下 list.append 的原子性是侥幸不出事；「append + 主循环 list 重建」交错仍可能丢事件；`Event.set()` 跨线程属未定义行为，偶发唤醒丢失极难复现。

**建议**

1. 主循环启动时把 loop 句柄注册给 social/nudge（如 `ev.social.set_main_loop(loop)`），弹幕线程统一走 `loop.call_soon_threadsafe(engine.observe, ...)`；
2. `wake.poke()` 改线程安全版本（持主循环引用后 `call_soon_threadsafe(_event.set)`）；
3. `NudgeEngine` 对 `burst_window`/计数加一把 `threading.Lock`（开销可忽略），或把可变状态收进 dataclass 整体替换（赋值原子）。

**收益**：消除偶发丢契机/丢唤醒这类最难排查的抖动。

## P1 — 架构与健壮性

### 4. 双唤醒机制并存，互不相通

**现状**：`ev/social/wake.py` 有完整的潜水/唤醒（WakeConfig + wait_for_window + 持久化 + 工具），但主循环实际用的是 `ev/kernel/handlers/input.py:40` 的 `runtime.proactive._wakeup.wait()` + `next_wake_in()`。LLM 调 `set_wake_config` 潜水后，**主循环根本不感知**（`next_wake_in` 不读 wake 配置），工具等于只写了个文件。

**建议**（二选一）

- 短平快：`ProactiveEngine.next_wake_in()` 接入 wake 状态——`is_sleeping()` 时返回 `min(wake_at - now, 现值)`；`heartbeat` 闸门加一条 `wake.is_sleeping() 且唤醒条件未触发 → return False`；`cancel_wake` 后 `_wakeup.set()` 立即醒；
- 彻底：主循环等待源统一换成 `ev.social.wait_for_window()`，proactive `_wakeup` 作为 poke 源之一。

**收益**：`set_wake_config` 从"摆设工具"变成真实生效的自主潜水。

### 5. deliberation 与 DanmakuPicker 两套评分并行

**现状**：`ev/danmaku/picker.py` 已有成熟的兴趣度评分/候选池/批量回复；v0.11 引入的 `ev/social/deliberation.py` 是另一套 0~1 分打分（默认关闭）。

**建议**：不做并联闸门，改做**信号融合**——把 deliberation 的信号（@我/引用/叫名/SC/礼物/复读/纯表情）作为加分项注入 picker 的 `_score`（如 `picker.submit(..., social_bonus=...)`），`should_block` 只保留黑名单硬过滤。避免同一条弹幕被两套阈值各判一次。

**收益**：一套评分口径，行为可解释；social 信号真实影响"回哪条"，而不是另开一个并行开关。

### 6. 启动 12 组件纯串行

**现状（证据）**：`ev/kernel/runtime.py:164-175` 依次 `await avatar/memory/evolution/mcp/tts/mindcraft/filter/llm/proactive/plugin/agent/io.setup()`。

**建议**：无依赖组件分组并行（`asyncio.gather(..., return_exceptions=True)` 保住"失败不阻断"）：`memory ∥ mcp ∥ tts ∥ filter`；`llm（依赖 mcp）→ proactive/plugin/agent`；`io` 保持最后。

**收益**：启动时间约等于最慢组件而非总和（TTS/记忆初始化通常是大头）。

### 7. 心跳空转轮询

**现状（证据）**：`ev/llm/proactive/policies.py:186` `next_wake_in()` 默认返回 `random.uniform(RESPONSE_INTERVAL_MIN, MAX)`（5~10s）；契机门控后绝大多数心跳在 `nudge.check()` 未命中时直接 return（`executor.py:71-73`），纯空转。

**建议**：`next_wake_in` 结合契机时间轴精确计算——取「最近事件时间 + long_silence 阈值」「上次 AI 发言 + silent_too_long 阈值」「冷却到期时间」的最小值，再与现有随机值取 min。契机不可能命中的时段干脆不醒。

**收益**：空闲唤醒频率从 ~0.1~0.2Hz 降到按需；逻辑集中在一个函数，改动小。

### 8. `ev/social` 半接线状态要收口

**现状**：`bootstrap.on_post_event / handle_nudge / wait_for_window` 目前无调用方（注释标了"可选"）；`social_wait_for_window` 与主循环实际等待机制平行。

**建议**：二选一——要么配合 #4 在 `input.py`/`application.py` 真正接线，要么把这三个函数降级为实验 API（`__init__` 去掉导出 + 文档标注）。**不要让"看起来能用"的公共 API 长期无人调用**（误导后续维护）。

## P2 — 工程化与体验

### 9. 测试与 CI

- 现状：仅 `tests/test_proactive_nudge.py`（284 行）；`ev/social`（v0.11 新增 ~2700 行）、emotion 向量化、config loaders、DanmakuPicker 全靠手工冒烟；无 `.github/workflows`。
- 建议：补四块最小测试——`tests/social/test_smoke.py`（本次调通的冒烟脚本直接固化）、`reaction` 向量分类（mock provider）、`silence.strip_markers/on_ai_final`、config loaders 的 SOCIAL 字段。加 GitHub Actions：`pytest + ruff check`，用 Windows runner（项目强 Windows 属性）。

### 10. 依赖锁定

- 现状：`requirements.txt` 里 `openai>=1.0.0`、`blivedm` 未锁版本。
- 建议：`pip-compile` / `uv pip compile` 生成 `requirements.lock.txt`，CI 用锁文件装；`blivedm` 这类小众库务必固定版本/commit（上游 API 一断，弹幕全挂）。

### 11. 控制中心暴露 SOCIAL_* 与契机统计

- 现状：`ui/pages/settings_page.py` 无 SOCIAL_* 字段；`ProactiveEngine.get_stats()` 已有 `nudge_acted/rejected` 等数据但无 UI。
- 建议：设置页加"拟人化"分组（8 个关键开关：EVENT_DRIVEN / ENGAGEMENT / DELIBERATION / QUOTE / SILENCE / LEARNING / SILENCE_RATE / SPEAK_TOOLS）；状态页加契机接受率小面板（数据现成）。

### 12. 文档缺口

- `configs/config.example.yaml` 未补 `SOCIAL_*` 段（v0.11 新增 21 个字段）；
- 仓库根无 README（上次提交有意移除——建议至少放极简引导页，或确认这就是最终决定）；
- `docs/` 补一篇 `ev-social.md`：模块图 + 接入点 + 工具协议（素材可精简自 `新建文件夹/EV-Anthropomorphic/docs`）。

### 13. EmotionIntent 双重名

- `ev/emotion/reaction.py:EmotionIntent`（7 字段 dataclass）与 `ev/llm/utils/embedding.py:215:EmotionIntent`（emotion+score）重名易混。建议后者改名 `EmotionScore`，或 reaction 直接复用并扩展。改动小、纯可读性收益。

### 14. 学习沉淀循环事件化

- `bootstrap._start_learning_loop` 的 5min sleep 循环是全项目唯一后台定时器。可改为挂在心跳/契机上：事件计数 + 时间阈值防抖后调 `consolidate_once()`，彻底兑现"零定时器"的设计口径。

### 15. 仓库小瘦身

- `ev/danmaku/blivedm/.history/` 有 2 个带时间戳的历史副本被 git 跟踪——删除 + gitignore；
- `.gitignore` 的 `data/emotion_embedding_cache.npz` 可复用为 #1 的缓存文件名。
