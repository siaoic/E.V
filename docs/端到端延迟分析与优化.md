## 1. 结论速览

**文本输入 → 出声（10 轮实测，智谱 glm-4-flash）**

| 指标 | min | avg | p50 | max |
|---|---|---|---|---|
| LLM 首字 | 1.599s | 2.034s | **1.923s** | 3.403s |
| 首句 TTS 入队 | 1.614s | 2.133s | 2.002s | 3.413s |
| TTS 首块（句内） | 0.255s | 0.315s | 0.320s | 0.347s |
| **端到端出声** | 1.931s | 2.448s | **2.322s** | 3.668s |

**换 API 前后对比（p50）**

| 指标 | minnimax（旧） | 智谱 glm-4-flash（新） | 变化 |
|---|---|---|---|
| LLM 首字 | 1.962s | 1.923s | **−39ms（基本持平）** |
| 首句入队 | 2.029s | 2.002s | −27ms |
| TTS 首块 | 0.338s | 0.320s | −18ms |
| 端到端出声 | 2.332s | 2.322s | −10ms |
| 首轮长尾 | 4.124s | 3.403s | −0.7s（懒加载仍在，见 A-4） |

> 结论：两家供应商 TTFT 同量级，换 API **没有解决瓶颈**；LLM 首字（~1.9s，占语音端到端 ~62%）仍是首要瓶颈。

**语音说话 → 出声（由分项实测合成的模型）**

```
说完 → VAD确认静音(0.6s) + 残余end推理(0.11s) + 交付(<0.01s)   ≈ 0.71s
     → LLM 首字(p50)                                          ≈ 1.96s
     → 首句早产值(平均)                                        ≈ 0.05s
     → TTS 首块(p50)                                          ≈ 0.34s
     → 声卡出声（口型/字幕同步触发）
端到端 ≈ 3.1s（p50）；最好 ≈ 2.4s；最差 ≈ 5.3s
```

**瓶颈定位（按占比）**

| 环节 | 耗时(p50) | 占语音端到端比 | 结论 |
|---|---|---|---|
| LLM 首字（网络+TTFT+注入组装） | ~1.92s | **~62%** | **首要瓶颈** |
| VAD 静音确认 | 0.60s | ~19% | 固有等待，可调参 |
| TTS 首块 | 0.20~0.34s | ~7~11% | 已优化到位 |
| ASR final 推理 | ~0.11s | ~3% | 忽略 |
| 主循环/队列/交付 | <0.01s | ~0% | 忽略 |

## 2. 链路架构与延迟测量点

```
麦克风 ─100ms块→ 采集队列 ─→ VAD(fsmn-vad, 200ms粒度) ─静音0.6s切段─→ commit
                                   │ 说话中每600ms feed
                                   ▼
                        ASR服务(127.0.0.1:8487, HTTP)
                        partial: p50 110ms/块（并行于说话，不计入延迟）
                        end收尾: p50 106ms ──→ final文本
                                   │ asyncio Future
                                   ▼
              主循环 wait_input 唤醒 ──→ converse（可打断）
                                   │
        ┌──────────────────────────┤ 以下全部计入「LLM首字」
        │ 知识闸门判定 → 知识检索（首轮1488ms / 命中缓存后2~4ms）
        │ 记忆召回（首轮1016ms / 快路径0ms；硬超时熔断1.5s）
        │ prompt组装（stable/volatile分层，服务端前缀缓存）
        ▼
        LLM 流式API（智谱） ──首字──→ 打字机 + 分句chunker（首段6字早产切）
                                   │ final句
                                   ▼
        TTS pump线程：GSV token级流式（25 token/块）
          cut_text 0ms → phones+bert 30ms → gpt首yield 105ms → vq.decode 40ms
                                   │ 首块 AudioClip
                                   ▼
        声卡出声 + 口型曲线(_on_play) + 字幕SSE(8765) 同步触发
```

观测结论：
- **首字 ≈ 首句入队**（差 15~400ms）——首段早产切分生效，首字后 6 字即切，几乎不额外等待。
- 智谱首轮长尾 0.7s 来自知识库懒加载（993ms）+ 记忆首轮检索（875ms），之后命中进程内缓存降到 <5ms；比旧供应商略快但问题同源。
- **两家 p50 首字同在 1.9s 量级（智谱 1.923 vs minnimax 1.962），换供应商未改变瓶颈**。智谱波动更小（max 3.4s vs 4.1s），稳定性略优。
- Butler 记忆提取走 SiliconFlow 并行执行，期间仍出现 3 次 `400 Bad Request`（thinking 参数不支持→降级重试），不阻塞主链路但浪费带宽与请求。

## 4. 延迟构成公式

```
文本场景：T(text→voice) = LLM首字 + 首句早产值 + TTS首块
语音场景：T(说完→voice) = T_vad(0.6s) + T_asr_end(0.11s) + T(text→voice)

LLM首字 = T_inject(知识+记忆检索，缓存后<10ms) + T_prompt(<5ms) + T_network(TTFB) + T_ttft(服务端)
```

当前 p50 分解（语音场景 ≈3.0s）：VAD 0.60 + ASR 0.11 + 注入 0.01 + 网络与服务端首字 ~1.91 + 早产 0.08 + TTS 0.32。

## 5. 优化路线图（按预期收益排序）

### A. LLM 首字（预期收益 0.5~1.5s，最大头）

1. **供应商/模型 TTFT 对比**：首字里注入与组装 <10ms，其余全是网络+服务端 TTFT。
   用 `bench_e2e_latency` 换 `LLM_BASE_URL/LLM_MODEL` 逐一实测，选 p50 TTFT 最低的组合。
2. **服务端前缀缓存命中确认**：stable/volatile 分层已实现（inner_loop.py），确认服务商支持
   context caching（智谱/SiliconFlow 均支持），并把 stable 段字节稳定性保持住（勿插入时间戳等易变内容）。
3. **volatile 段瘦身**：知识/记忆注入文本越短，TTFT 越短。可设注入字数上限并观测首字变化。
4. ✅ **首轮懒加载预热**：知识库首次检索 1488ms 只应在启动预热阶段发生
   （把 `_knowledge_section` 的数据加载挪到 `brain.warmup()`），消灭第一轮长尾。（已落地：
   `KnowledgeService.preload()` 由 `brain.warmup()` 后台 `asyncio.to_thread + wait_for(15s)` 调用，失败静默）

### B. 注入检索并行化 + 熔断收紧（预期收益 0~1.5s，仅未命中缓存/慢路径时）

5. ✅ 知识检索与记忆召回当前串行 await，可 `asyncio.gather` 并行；记忆熔断 1.5s 可收紧到
   0.8s（实测快路径 0ms，1.5s 熔断仅在检索服务异常时触发，此时注入价值本来就低）。（已落地：
   `inner_loop.py` 记忆召回先 `ensure_future` 与知识/画像本地检索段并行，末尾 `wait_for` 汇合；
   `_MEMORY_RECALL_TIMEOUT` 1.5→0.8s）

### C. VAD 切段参数（预期收益 0.1~0.2s，体验权衡）

6. `STT_SILENCE_SECONDS` 0.6→0.45~0.5s 实测主观断句效果；过短会在用户停顿时误切。
   该参数已是 .env 可调项，无需改码。

### D. 小项（合计 <0.1s，可选）

7. ✅ Butler 的 `thinking` 参数对 SiliconFlow 必 400 再降级——按服务商能力直接发兼容参数，
   省一次往返（不占关键路径，但降低并发带宽压力）。（已落地：`factory.py` 进程内
   `thinking_is_supported()/mark_thinking_unsupported()` 按「base_url|model」记忆；
   `butler_agent/core.py` 已知不支持直接省略 `extra_body`，降级时记号，429 不误判）
8. TTS 首段早产 6 字→4 字试验：首字→首句入队能再省 ~0.1s，
   需验证 GSV 对超短文本（"我是一个"级别）合成的稳定性。
9. `empty_cache` 保持默认开启（关闭仅省 5ms，不值得冒显存碎片风险）。

### 不建议再投入的方向

- TTS 首块（~200ms，接近模型下限）；
- ASR feed/end 推理（110ms，远小于块粒度）；
- 进程内队列/交付（<1ms）。

### 测量注意事项

- bench_e2e 的「端到端出声」= 首块音频就绪（打桩不出声），线上真实出声还需加声卡缓冲（<50ms）。
- 「本轮对话/端到端」埋点包含 TTS 全部播完的 drain 等待，**不能**当作出声延迟。
- 语音场景无法脚本化全自动（需真实麦克风说话），用第 1 节公式 + 分项实测合成即可。
- 实测前先跑一轮预热对话，排除模型冷启动干扰。
- 首轮对话固定有知识/记忆懒加载长尾（~2.5s），评估优化效果请以第 2 轮起为准（或先做 A-4 预热）。
