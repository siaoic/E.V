## 2. 已知问题与约束

- **开场多样性尚未实测**：话题池已实现（`LLM_TOPICS` 环境变量或 `config.topics`，启动时洗牌，开场窗口弹出一条注入——中段不再由机制换题，见 ADR-0009，池空回退模型自选，见 `src/llm/plugin.ts`），但从未用真实清单跑过长测，「开场是否多样化、`memory_save` 是否被主动使用」仍是未知（见 3.1 第 1 项）。本文此前误记「话题池配置已随冷场一起删除」，与第 35 行及代码不符，2026-10-11 修正。
- **话题连续性尚未实测**：删掉按句数强制换话题后，长测要观察「同一话题连续句数」的分布（见 ADR-0009 的验收口径）；若出现连续 30+ 句死磕一个话题，再上「话题枯竭度 → 素材注入」的回退方案，而不是恢复句数计数。
- **`run-live.bat` 本体必须保持纯 ASCII（2026-10-11 实测）**：`chcp 65001` 之下 cmd.exe 用控制台代码页解码批处理文件，文件里任何 >0x7F 的字节都会让它的读取位置前移，**后续每一行被吞掉开头若干字符**（实测 `set "TTS_DIR=…"` 变 `IR=…`、`if errorlevel` 变 `orlevel`、`REM …<repo>…` 里的 `<` 直接变成重定向并报「系统找不到指定的文件」），于是 `if`/`start` 静默走错分支——改写前那版脚本里恰好有「如果用 UTF-8 无 BOM 存盘就会如此」的情形，而它**从未在本机真正跑过**（旧表「已完成，未在本机实际运行过」就是征兆）。UTF-8 BOM 也救不了（同样实测错位）。因此脚本里不写中文：项目路径取 `%~dp0`，语音文件名从 `.env` 用 `for /f` 读出后由子进程继承（`node -e` 实测收到完整的 `voices/灰原哀.json`）。**改这个脚本时先自查字节：不能出现任何 >0x7F 的字节。**
- **配置只有一个落点：`.env`（2026-10-11）**：`src/main.ts` 启动即加载它，且**已存在且非空的环境变量优先**——所以脚本/命令行里 `set` 的同名变量会盖掉文件。排查「改了配置不生效」先看是不是被外层环境变量顶掉了（真机日志 `[env] … ；环境变量优先保留 X` 会点名）。
- **当前 LLM 端点（2026-10-11 更新）**：`.env` 指向 **AMD Radeon 的 OpenAI 兼容端点** `https://developer.amd.com.cn/radeon/api/v1`，模型 `DeepSeek-V4-Flash-Vision-Exp`（自带视觉，视图调用不必另配 `VISION_MODEL`）。真机实测一句开场白 **1.4 秒**返回，远低于 7 秒超时。**该端点不认 `thinking`**：配了会回 400 `unsupported_parameter`，靠 client 的「去掉 extraBody 重发一次并记住」兜住（每进程只白撞一次，日志会打 `[llm] 端点不接受 extraBody，已去掉重发`）；已从 `.env` 移除该参数。`client-plugin.ts` 的默认值只在 base URL 含 `bigmodel.cn` 时才补 thinking-disabled，对 AMD 不生效（符合预期）。消息列表必须以 user 结尾（不发用户消息会被 400 code 1214 拒绝），工具结果之后会追加一条 user 消息。
- **图片说明只认 http(s) URL（2026-10-11 实测，AMD + `DeepSeek-V4-Flash-Vision-Exp`）**：模型自带视觉（拿一张公网图片实测 2.9 秒返回正确描述「蓝色背景，白色字母 TS」），但**该端点不接受 `data:` URL**——传 base64 data URL 会 500 `broken data stream when reading image file`（用 70 字节的合法 1×1 PNG 复现过，排除测试图本身问题）。因此 `describeImage` 只在图片是**公网可访问的 http(s) 地址**时有效；`memory_save` 带图若给的是本地路径或 data URL，会在这条端点失败并**静默降级**（[src/memory/hooks.ts](../../src/memory/hooks.ts) 的设计是看图失败就要求模型自己补一句描述再存）。弹幕本身不带图，所以这条目前不影响直播主链。
- **上一端点：GLM Coding Plan（历史记录）**：`https://open.bigmodel.cn/api/coding/paas/v4`、`glm-5.3-flash`，必须关 thinking 否则响应超 7 秒；2026-10-11 实测返回 `1310 您已达到每周/每月使用上限，限额将在 2026-10-15 20:52:33 重置`（不同账号，与现在的 AMD 端点无关）。配额耗尽的表征是「直播不说话」，降温机制按预期接管（暂停 10 个心跳、弹幕只进缓冲）。
- **账户速率限制**：端点返回 `429`（GLM 是 `1302 您的账户已达到速率限制`）时，client 退避重试**至多 4 次**后抛错（此前这条路径没有次数判断，会每 4 秒永远重试下去，把窗口永久挂住、直播无限期不说话）；窗口层收到 `rateLimited` 标记后暂停 10 个心跳（约 21 秒，心跳实测每 2.01 秒一拍）再恢复，降温期弹幕只进缓冲。真机仍频繁限流属端点配额问题（D6）。
- **TTS 截断风险**：`E:\AI\Qwen3-TTS-GGUF\server.py` 的 `max_steps=500` 是单句生成上限，超过会在句中停止，尚未验证它对应多少秒音频。
- **弹幕回复滞后**：句子在播报前生成，弹幕要等当前句播完才会被回应。已通过"只读未读弹幕 + 句子压短"缓解，需要实测确认。
- **WebSocket 关闭握手约 5 秒**：B 站服务器不及时回应关闭帧，Node 在约 5 秒后才发出 `close` 事件。CLI 脚本通过 `process.exit(0)` 绕过；常驻主程序不受影响。
- **所有超时不超过 7 秒**（用户规则，已记入记忆）。长测使用超时参数 `0` 表示挂机，需要手动停止，这是唯一例外。
- **弹幕取法已与词汇表对齐（2026-10-11 完成）**：注入式重构后，接话分层在入口/组装侧标记（A/B 逐条、C 层聚合成一行计数、D 层不出现），弹幕不再由模型主动拉取（`read_danmaku` 已删除）。原先这条「取法与词汇表定义不一致」的已知问题随之关闭。
- **TTS 服务需先启动**：`cd E:\AI\Qwen3-TTS-GGUF && PYTHONUTF8=1 TTS_ONNX_PROVIDER=CUDA TTS_VOICE_JSON="voices/灰原哀.json" .venv/Scripts/python.exe server.py`（不带 PYTHONUTF8=1 会因 GBK 控制台下的 emoji 打印崩溃；日志在 `log/latest.log`）。服务是单线程 HTTP，同一时刻只处理一句。
- **TTS 速度实测（RTX 4060 Laptop，2026-10-09）**：模型必须用 `model-base-small`（custom-small 的 ONNX 解码器慢 8 倍）。修复后 RTF 0.35-0.36，首音延迟 0.43s。注意 f16 量化档有采样越界 bug，保持 q5_k+q8_0。
- **话题仍可能跨窗口延续**：新弹幕可能引用旧话题，发言守门只拦截完全相同的句子。
- **弹幕取法与词汇表定义不一致**：`CONTEXT.md` 把接话分层定义为「投递时由入口插件标记」，C 层聚合为背景摘要、不逐条进上下文，D 层默认忽略；当前实现是模型主动调用 `read_danmaku` 拉取未读 10 条，既无分层、也无背景摘要。取弹幕的方式先对齐，分层才有落点（见 3.3 第 6 项、4.D7）。
- **人格档案的恢复动作只能由模型自己完成**：版本层补齐后，旧版一定取得回来（`git_log`／`git_show`），但**没有任何自动回滚**——Cortico 也没有，它靠人工 checkpoint 加两道确认；我们没有控制台，所以「发现缩水 → 抄回旧版」这条闭环目前只由模型在下一窗看到摘要提示后自行完成，尚未实测。
- **记忆无去重**：同一件事可以被记两条（工作区 `memory.jsonl` 实测：第 3 条「和妈妈买彩票中了两百块…」与第 4 条「陪妈买彩票中200元炖鸡汤…」是同一次聊天）。「别重复」只进提示词，写入期没有相似度检查或合并。**Cortico 也没有语义去重**（`bots/cormini/persona/handoffNote.ts:200-216` 只做逐字精确匹配折叠），这条若要做得自己发明。
- **心跳实测（2026-10-11，房间 22748536，150 秒，`plugins/90-danmaku/heartbeat-probe.ts`）**：心跳 74 次，间隔**平均/中位 2.01s**（最小 1.72 / 最大 2.29），与插件默认 `HEARTBEAT_MS=2000` 一一对应（B 站对每个心跳都回一次）；同期弹幕 93 条，其他事件 0 条。复测命令：`node plugins/90-danmaku/heartbeat-probe.ts 22748536 150`。由此推出：`dream` 的 `every=30` 是**约 1 分钟一轮**（要半小时需 900 拍）；429 降温 10 拍约 20 秒。
- **心跳不带人气值**：上条实测里 74 次 `HEARTBEAT_REPLY` 的 `count` **全是 `null`**（空包体）。架构里当作背景数据注入的「热度水位」（观众数/在线时长）目前拿不到任何数值，`live-smoke` 打出来的 count 也一直是未知。要这个数据得另找接口（观众数需另接 HTTP 接口或 `ONLINE_RANK` 一类命令）。
