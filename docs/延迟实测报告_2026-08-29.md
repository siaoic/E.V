## 2. 延迟瀑布（以 T02 转录还原，干净轮）

```
0        ── 注入「你叫什么名字？」
+70ms    ── 情绪分类（「厌恶」→ 误判，见 F7）
+2460ms  ── 知识库判定完成（检索 1.2ms，快）
+2494ms  ── 记忆快路径 31ms（embedding 服务已预热：8081 llama-server）
+2460ms→+10436ms  ── ★ LLM TTFT ≈ 8s（glm-5.3-flash，含 24 工具 schema 的大 prompt）
+10436ms ── 首字「深海风花…」（人设回答正确）
+11.1s   ── TTS 首句实际出声（★ 距首字 +7~12s，远超 bench 首块 0.32s，待查）
```

**结论：当前链路的两大黑洞是 ① LLM TTFT（~8s 级）与 ② 文本→出声（+7~12s 级）。** prompt 组装/知识/记忆/工具调度均已在百毫秒级，不是瓶颈。

### 2.1 追加定位（2026-08-29 深夜）：「文本→出声」的黑洞不在 TTS

用逐字转录时间线 + `ev.tts.bench_stage_breakdown`（30 轮合成，llama-server 同卡占用下实测）复核：

```
TTS 合成首块 p50 = 265~272ms（cut 0ms → phones/bert 30ms → gpt 首 yield 147ms → vq decode 55ms）
   ↳ 与 8/28 基线 0.32s 一致，GPU 争用/角色权重均未劣化 → TTS 侧无罪
干净轮实测「真实首字 → 出声」只加 0.6~1.3s：
   T04  首字 9900ms → 出声 11197ms（+1.3s）
   T02  首字 10436ms → 出声 11056ms（+0.6s）
出声时刻 ≈ 第 20 字时刻 + 0.5~3.6s —— 出声贴着文本流走
```

因此「first_text 2.4~3.5s → 出声 9~15s」的真实构成是：
1. **LLM token 流出速度慢/不均（主因）**：glm-5.3-flash + 24 工具大 prompt 下，逐字节奏两种形态——慢流（T03 ≈2.1 字/s、T06 ≈3.6 字/s）与「长等 + 爆发」（T04 等 9.9s 后 45 字/s）。首段早产切分要攒 6 字，攒齐时刻被流的形状拖到 8~16s；
2. **首段阈值**：`_FIRST_SEGMENT_MIN_CHARS=6`（防 GSV 短文本不稳），出声天然晚于首字 6 个字；
3. **工具轮串行**：工具夹在中间时（T05 看屏 39s）TTS 被整体推后；
4. TTS 本身合计仅 ~0.3s 合成 + ~0.2~1s 播放启动。

**可执行优化（按收益排序）**：① LLM 侧——TTFT/token 吞吐 A/B（glm-4-flash vs 5.3-flash）、按 toolset 门控裁剪工具 schema 数量；② `_FIRST_SEGMENT_MIN_CHARS` 6→4 试验；③ TTS 侧已无可压。

### 2.2 切段规则调整（2026-08-29 深夜实施）：停顿标点遇号即切

**分层澄清**：`gsv_tts/TextProcessor.py: cut_text()` 与 `inner_loop` 的切段**不重复、是接力**——前者在 `infer_stream` 内部对**已到手文本**做语义分块（`cut_minlen=10` + 停顿集 `，,；;：:~・…` + `cut_mute` 静音），管不了「还没从 LLM 流出来的字」；后者决定**何时交出第一段**，是首声时机的唯一控制点。

**已实施**：`_PAUSE_ENDS` 增补 `；;` 且 `_PAUSE_SEGMENT_MIN_CHARS 4→0`（`ev/llm/cleaners/sentence.py` + `inner_loop.py`）——1~3 字语气词开场（「等等，」）不再攒字，实测收益约 0.3~0.5s@2~4 字/s 吞吐；`；` 由不可切变为可切。单测 + 真机冒烟（`latency_e2e_20260829_230852.jsonl`）通过。

**A/B 后不做**：把 `_PAUSE_ENDS` 对齐 `cut_text` 的完整停顿集（补 `：:~・…`）——对 7 条真实回复（`latency_e2e_*.jsonl` 还原）统计，**0 条**的首个停顿是这些符号（开场全部是句号/逗号），扩展集零收益；且 LLM 侧拆得更碎会让 GSV 段间衔接变多，不如让 `cut_text` 在同一次合成流内用 `cut_mute` 处理这些停顿。

## 3. 发现清单（按严重度）

### P0（功能失效，建议立即修）

- **F1 看屏功能实际不可用**：`look_at_screen` 实际执行 >10s（Qwen3-VL 远程调用），被工具默认 10s 超时掐死 → 返回占位「执行超时，本轮跳过」，AI 盲答并二次调用。证据：T05 转录 `[WARN] ↳ 「look_at_screen」执行超时（>10s），本轮返回占位`。修法：`tool_registry` 注册时放宽 timeout（机制已有，`read_sheet_music` 就是 1500s），并考虑视觉调用前先出声 ack。
- **F2 「弹 <非乐谱文件>」无格式预检**：`弹 D:/score.txt` 直接触发 `play_score`（V2.0 用例 7 预言成真）；`弹 test_note.png` 触发 `read_sheet_music`（OMR）。修法：工具 description 加扩展名约束 + 执行前魔数/后缀校验 + 拒答话术。
- **F3 管道输入中文乱码**：主程序 `input()` 按 **GBK+surrogateescape** 解码 stdin，而控制中心按 **UTF-8** 写入（`process_handler.py: _send_text`）→ 控制中心发送框的中文全部损坏。模型亲口回复「你打的那行字，乱码」。控制台手打不受影响（WinConsoleIO）。修法：`main.py` 启动时对 `sys.stdin.reconfigure(encoding="utf-8")`（与既有 stdout 处理对齐）。harness 已临时用 cp936 写入绕开。

### P1（实时性红线）

- **F4 `read_sheet_music` 内联阻塞**：T01 中 OMR 在工具轮内同步执行，**静默 >90s**（中途无任何进度/ack），导致整轮无法收尾；非乐谱图也不做快速判废。违反 S11「先出声确认再后台识别」。修法：委派给后台 sub-agent（`maybe_delegate` 机制已有）或加「已开始识别」先行语音 + 完成后主动播报。
- **F5 文本→出声 +7~12s**：首句出声远慢于 `bench_e2e_latency` 的 0.32s 首块基线，且波动大（T04 两次 11.2s / 30.4s）。候选因素：TTS 泵/播放链（CABLE Input + vts_audio 口型）、首句切分时机、GPU 争用（测试后期 8081 embedding 占 ~1.1GB 显存）。需单独复跑 `bench_e2e_latency.py` 分离。
- **F6 LLM TTFT ~8s**：.env 已从 glm-4-flash（基线 1.92s）换成 glm-5.3-flash，实测 TTFT 抬升到 ~8s（工具 schema 24 个的大 prompt 下）。建议 A/B 两个模型各 10 轮后定版。
- **F7 首轮后置链路疑似阻塞**：每次冷启动后的**第一轮**对话结束 → 重新可输入之间观测到最长 ~150s 的静默（后续轮正常）。已排除 Butler（队列 worker）与进化复盘（AsyncOpenAI）；候选：首轮 Butler/情绪首次远程调用的同步段、TTS 链路收尾。注：harness 早期版本存在「残余 buffer 喂入时间戳伪影」，该数值上界不可靠，需程序内打点确认。

### P2（行为/质量）

- **F8 闲聊误路由技能**：`你好呀，随便聊两句` 3/3 触发 `load_skill`——技能意图打分过拟合。
- **F9 天气不调工具**：`明天上海天气怎么样？` 纯文本作答（T06 红线 S2 的防幻觉项）。
- **F10 C01 技能链不落地**：`play_piano_melody` 技能的「BPM 必须搜索」条款让模型连打 `bing_search`×2，150s 窗口内 `play_melody` 永不执行；建议技能内加「通儿歌/经典曲默认 tempo，用户强调原速才搜」的例外条款。
- **F11 工具返回非 JSON**：`get_current_time` / `load_skill` 返回纯文本（程序自身 WARN 提示了解析成本）。
- **F12 情绪误判**：名字提问被判「厌恶→黑脸」。

## 4. 测量方法说明与可信度

- **首字**：stdout 零宽标记 `\u2060`（console.CHAT_TAG）首现时刻 − 注入时刻；已剥 `你 >` 前缀与 ANSI 码；打字机 delta 无换行，已做部分缓冲实时喂入。
- **出声**：字幕 SSE（:8765 `/events`）首个 `event: text`（TTS 首块 `_on_play` 绑定推送）− 注入时刻。
- **轮次边界**：⏱ 报告/SSE clear 后等主循环重打印 `你 >` 提示符（wait_input 重入）才注入下一条；此前版本的边界缺陷（空闲 15s 误判、残余 buffer 时间戳伪影）已修复并在本轮数据中剔除污染轮。
- **未决口径**：内部 ⏱ LLM 首字 在多工具轮里是「末轮值」，与外部首字不可直接比；后续给 inner_loop 埋点加轮次序号再收口。
- **环境备注**：测试中发现 embedding 服务（8081）未启动 → 已代为启动并预热（`启动embedding.bat` 同参数），**该服务仍在后台运行**；未启动时记忆召回每轮吃 0.8s 熔断 + 情绪分类器初始化失败。
